# 阶段二 · 第 4 课讲义：RAG 与标准件思维

## 1. 动机闭环（回收第 2 课思考题 3）

第 2 课你答过：上下文窗口放不下、长对话成本平方级、lost in the middle。
三条全指向同一个解法：**不要把知识塞进上下文，要按需检索**。
所以一句话记住 RAG 的存在理由：**上下文窗口小，才需要 RAG。**

RAG 三段式（你在合规平台全手写过）：

```
离线：文档 → 切块 → 向量化 → 入库
在线：问题向量化 → 相似检索 top-k → 拼进 prompt → LLM 作答
防线：期望边界（拒答）+ 引用校验
```

## 2. 标准件对照表（面试讲"手写过 RAG"的底气来源）

| 你手写过的 | LangChain 标准件 | 换库时改哪 |
|---|---|---|
| embedding-3 API 调用 + 向量列表 | `OpenAIEmbeddings` | 只换 Embeddings 实现类 |
| 手写余弦相似度 + top-k | `InMemoryVectorStore.as_retriever()` | 换 Chroma/FAISS/Milvus 只换这一行 |
| 字符串拼接 prompt | `ChatPromptTemplate` | — |
| 防幻觉引用约束 | 写进 prompt 的期望边界 | 思想与框架无关 |

**标准件的价值**：接口统一 → 换向量库/换嵌入模型不动业务代码。
**你的差异化**：你知道每个标准件背后是哪 30 行手写代码——面试时能往下讲三层的人极少。

## 3. 检索质量决定 RAG 上限（第 5 课钩子）

向量检索的两种死法：
1. **用词不同、语义相同**（"降本" vs "节约成本"）→ embedding 能救
2. **精确匹配型**（工单号、错误码、人名缩写）→ embedding 经常救不了 → 需要混合检索（关键词+向量），第 5 课讲

所以盯 RAG 先盯检索：这课代码把每次命中的相似度分数打印出来，就是要你养成这个习惯（你 MT30 的 0.33 阈值直觉在真实数据上再校准一次）。

## 4. 期望边界（合规平台精髓，两层防线）

- **检索层**：分数低于阈值 → 召回不足 → 直接拒答，连 LLM 都不用调（省钱 + 可控）
- **生成层**：prompt 写死"片段不足以回答就说知识库没有，禁止编造"
- 你踩过的坑这里再确认一遍：两层都要。只有检索层 → 用户换个问法就穿透；只有 prompt 层 → 模型偶尔还是编。

## 5. 面试一句话：RAG vs 微调

> 知识更新频繁、要溯源、要控制成本 → RAG；固定领域的"行为风格/格式"需要内化 → 微调。
> 大多数企业知识问答场景 RAG 是首选——两者不互斥，可组合。
